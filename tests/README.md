# pbstools tests

This directory holds the tests for the pbstools utilities:

* **`launch_cf`**: automated test suites for Derecho and Casper, a dry-run suite
  that needs no scheduler, and a script that checks the results.
* **`qcmd`**: a script that runs `qcmd` with a set of resource requests, in
  [`qcmd/run.sh`](qcmd/run.sh).
* A few extra command files for trying `launch_cf` by hand.

There are no tests for `qinteractive` or `execcasper` yet.

## Quick start

On a Derecho or Casper login node, from this directory:

```
make check              # submit this system's launch_cf tests (check_derecho or check_casper)
qstat -u $USER          # wait for the jobs to finish
./check_results.sh      # summarize the results: PASSED, FAILED or NOT FINISHED
```

Anywhere, without submitting jobs:

```
make check_dryrun                 # generate the PBS scripts launch_cf would submit
./check_results.sh dryrun         # compare them with the saved copies
```

Before merging a change to `launch_cf` or `share/launch_cf.pbs`, run the dry-run
check and both system suites, `check_derecho` on Derecho and `check_casper` on
Casper.

## Before you start

* **Work in a clone on GLADE**, e.g. under `/glade/derecho/scratch/$USER`. The
  jobs write their output to the directory they were submitted from, and the
  cross-submission tests run on the other system, so that directory must be
  visible from both.
* **The tests submit real jobs**, which are charged to `SCSG0001` by default. Use
  another project with `make check account=PROJECT`.
* **`make check` picks the suite from `$NCAR_HOST`**, which is set on the login
  nodes. Use `make check_derecho` or `make check_casper` to choose one
  explicitly.
* **The first run builds two small OpenMP programs** with `gcc -fopenmp`, and
  downloads the source of one of them (`gs_openmp.c`) from GitHub with `wget`.
* **The tests use the `launch_cf` in this checkout** (`../bin/launch_cf`), not
  the one on your `PATH`. To test another copy, pass an absolute path, e.g.
  `make check launch_cf=/path/to/bin/launch_cf`.

## launch_cf tests

### Make targets

| Target | What it does |
|---|---|
| `make check` | runs `check_derecho` or `check_casper`, according to `$NCAR_HOST` |
| `make check_derecho` | submits the Derecho suite from `./derecho/` |
| `make check_casper` | submits the Casper suite from `./casper/` |
| `make check_dryrun` | generates the PBS scripts for the dry-run suite in `./dryrun/`, without submitting anything |
| `make save_dryrun` | regenerates the dry-run scripts and saves them as the new expected copies |
| `make clean_derecho`, `make clean_casper` | remove `./derecho/` or `./casper/`, and with them all of that suite's results |
| `make all` | builds `gs_openmp` and `omp_cmdfile` only |

Each system suite runs from its own subdirectory, which collects that suite's
results. The command files and programs it runs are built here and linked into
the subdirectory.

### What the suites test

All tests run with `-A $(account) -l walltime=0:10:00`. The command files are:

* **`cmdfile`**: 1200 `dd` steps.
* **`smalltest`**: 63 steps, fewer than fit on one node. Its first step,
  `env | sort | uniq`, records the job environment.
* **`omp_cmdfile`**: 510 runs of the OpenMP program `gs_openmp`, generated by
  `make`.
* **`hw_cmdfile`**: 6 runs of `hello_world_openmp`, which prints its thread
  count. Generated by `make`.

**Derecho** (`make check_derecho`), 6 jobs:

| Test | Options | Covers |
|---|---|---|
| defaults | `./cmdfile`, given implicitly | default command file; 128 steps per node |
| njobs < ppn | `./smalltest` | all steps fit on one node, so no job array |
| openmp | `--nthreads 4 --steps-per-node 32` | OpenMP steps |
| openmp hello world | `--nthreads 32 --steps-per-node 2` | threads reach the program; the checker verifies every step reports 32 threads |
| derecho -> casper | `-q casper@casper-pbs --ppn 32 --nthreads 4 -N ...` | submitting from Derecho to Casper |
| all args | `--processors-per-node 128 --nthreads 8 --steps-per-node 16 --memory 100G --queue preempt --cpu_type milan --random_start_delay 5 -N ...` | every `launch_cf` option at once |

**Casper** (`make check_casper`), 4 jobs:

| Test | Options | Covers |
|---|---|---|
| defaults | `./cmdfile`, given implicitly | Casper's default of one CPU per job, so a 1200-element job array |
| njobs < ppn | `./smalltest` | 63 single-step array elements |
| openmp | `--nthreads 4 --steps-per-node 8` | OpenMP steps |
| casper -> derecho | `-q main@desched1 --nthreads 4 -N ...` | submitting from Casper to Derecho |

The "all args" test runs on the `preempt` queue on purpose, so the scheduler
can stop it part way through. See [PREEMPTED](#reading-the-results) below.

### What a run leaves behind

In `derecho/` or `casper/`:

* **`<job name>.o<job id>.<index>`**: the PBS output of each array element, or
  `<job name>.o<job id>` for a job that isn't an array. Job names are
  `launch_cf` unless the test sets `-N`.
* **`stdout-<job id>.<server>/step-NNNNN.out`**: the output of each step from
  the command file.
* **`launch_cf.<command file>.<timestamp>.pbs`**: the job script `launch_cf`
  generated and submitted. You can inspect it, or resubmit it with `qsub`.
* **`results.csv`**: timings that `gs_openmp` appends on every run.

### Checking the results

Once the jobs have finished, run `./check_results.sh` from this directory. It
checks the suite named by `$NCAR_HOST`, or the one you give it:

```
./check_results.sh                 # this system's suite
./check_results.sh casper          # a given suite, in ./casper/
./check_results.sh derecho DIR     # a given suite, with results in DIR, e.g. copied elsewhere
```

It reads the PBS output files and step logs, and prints one line per test:

```
 [PASS]      openmp               job 7820719 (launch_cf): 16/16 subjobs, 510 steps, 32 steps/node x 4 threads/step, longest subjob 15s
 [PREEMPTED] all args             job 7820721 (all_args_test): 32/32 subjobs, 510 steps, 16 steps/node x 8 threads/step, longest subjob 61s
        - subjob(s) 7,11 stopped part way; 17 of 510 steps never started, ... PBS reports the scheduler stopped them, i.e. preempted
        - rerun the test to complete it

Result: NOT FINISHED (5 passed, 1 preempted, 0 not finished)
```

#### Reading the results

| Status | Meaning |
|---|---|
| `PASS` | every array element finished, every step ran exactly once and left a log, and no output shows an error |
| `FAIL` | something went wrong; the lines below it say what |
| `WAIT` | no output yet from the test, or from some of its array elements; they are probably still queued or running |
| `PREEMPTED` | array elements stopped part way without an error, most likely because the scheduler preempted them; rerun the test |

A test **fails** if, for example:

* the PBS output shows an error, such as a job killed for exceeding its walltime;
* an array element finished without running all of its steps;
* a step ran twice;
* a step log shows a crash, such as `Segmentation fault`, `command not found` or
  `Killed`;
* a hello world step reports the wrong thread count.

For **`PREEMPTED`**, when `qstat` is available, the script asks PBS whether the
scheduler terminated the stopped elements. If PBS confirms it, the line says so.
If PBS gives another reason, the test is a `FAIL`. If PBS no longer has the job,
the line says "most likely preempted" and gives the `qstat -xf` command to
confirm it.

The overall result and exit status are:

* **`PASSED`**, exit 0: every test passed.
* **`FAILED`**, exit 1: at least one test failed.
* **`NOT FINISHED`**, exit 2: nothing failed, but some tests are still waiting
  or were preempted.

The script also reports any job of the suite that stopped before it could be
matched to a test.

**How tests are matched to jobs.** Several tests share the job name
`launch_cf`, so the script identifies each test's job by its name, step count,
steps per node and threads per step, which every job prints. If a test was run
more than once, the newest job is checked and the older ones are ignored. To
start over, run `make clean_derecho` or `make clean_casper`.

### The dry-run suite

`make check_dryrun` runs `launch_cf --dryrun` for five combinations of options,
writing each generated PBS script to `./dryrun/` without submitting it. It
always uses Derecho's settings (`NCAR_HOST=derecho`), so it gives the same
results on any machine, including a laptop.

`./check_results.sh dryrun` then compares each script with its saved copy in
`./dryrun_expected/`. It ignores when and where the script was generated, and
reports any other difference as a `FAIL`, with the lines that differ.

If you change what `launch_cf` generates on purpose:

1. Run `make check_dryrun` and `./check_results.sh dryrun`, and check that the
   differences are the ones you intended.
2. Run `make save_dryrun` to replace the saved copies.
3. Commit the updated `dryrun_expected/` files along with your change.

A new dry-run test fails with "no saved copy" until you save it the same way.

### Adding a test

* **To a system suite:** add a `launch_cf` line to `check_derecho` or
  `check_casper` in the [`Makefile`](Makefile). Then add a matching line to
  `expected_tests` in [`check_results.sh`](check_results.sh), which must stay in
  sync with the Makefile. Its fields are label, job name, command file, steps
  per node and threads per step. The combination must differ from every other
  test in the suite with the same job name, so give the new test its own `-N`
  if it doesn't.
* **To the dry-run suite:** add a line to `check_dryrun` with its own
  `--script ./dryrun/NAME.pbs`, check the generated script, then run
  `make save_dryrun`.

## Other command files

These aren't run by any target. Use them to try `launch_cf` by hand, e.g. from a
scratch subdirectory:

```
../bin/launch_cf -A PROJECT -l walltime=0:10:00 ./redirection
```

* **`developtest`**: 4 steps, where step 3 redirects its own output to
  `step3.out` and `step3.err` in the submission directory.
* **`redirection`**: 63 steps. The first 16 redirect their output to
  `out.${step}.log`, which tests that command-file lines can use the `${step}`
  variable `launch_cf` sets. `${step}` counts from 0, so expect `out.0.log`
  through `out.15.log`. Their logs under `stdout-*/` stay empty.

## qcmd tests

[`qcmd/run.sh`](qcmd/run.sh) runs `qcmd ... -- mpirun hostname` with a set of
resource requests for the current system, Derecho or Casper, according to
`$NCAR_HOST`. Each run has a 60-second timeout. It doesn't check the results:
each run should print the host names of the nodes it got, so read through the
output.

To test the `qcmd` in this checkout rather than the one on your `PATH`:

```
cd qcmd
PATH=$(cd ../../bin && pwd):$PATH ./run.sh
```
